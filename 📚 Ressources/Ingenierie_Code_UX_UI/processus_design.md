Les designers (et designers-ingénieurs) ne partent pas de « ce qui est joli », mais d’un **processus structuré** qui combine recherche, exploration, critères objectifs et tests. 
## 1. Comprendre le problème avant de designer

Avant d’ouvrir Figma, ils passent du temps en **phase de découverte** :

- **Objectifs business** : qu’est-ce que le site doit accomplir ? (vendre, informer, générer des leads, etc.) 
- **Utilisateurs cibles** : qui sont-ils, quels sont leurs besoins, leurs contextes, leurs frustrations ? 
- **Contraintes** : budget, délais, technologies, contenu existant, SEO, accessibilité, etc. 

Méthodes typiques : entretiens utilisateurs, questionnaires, analyse des analytics, benchmark concurrentiel, ateliers avec le client.

> Règle clé : on ne conçoit pas pour soi ou pour le client, mais pour les **utilisateurs réels** et leurs besoins. 

## 2. Structurer l’information (UX avant UI)

Une fois le problème clarifié, ils définissent la **structure** du site :

- **Arborescence** : quelles pages, comment elles s’organisent. 
- **User flows** : comment l’utilisateur passe d’un point A à un point B (ex : arrivée sur la homepage → comprendre l’offre → contacter).
- **Wireframes** : maquettes fil-de-fer qui placent les blocs (menu, hero, CTA, témoignages, footer) sans design. 

À ce stade, la question n’est pas « c’est beau ? », mais « est-ce que ça répond au besoin et que c’est clair ? ». 

## 3. Explorer des idées visuelles (idéation)

Pour l’aspect visuel, les designers utilisent plusieurs techniques :

- **Moodboards / planches de tendances** : collections d’images, couleurs, typographies, références pour capter une ambiance. 
- **Sketching rapide** : plusieurs versions de layouts, de grilles, de hiérarchies visuelles.
- **Benchmark visuel** : regarder ce qui se fait dans le secteur (et ailleurs) sur des sites comme Awwwards, Behance, Dribbble, Pinterest. 

L’idée est de **générer beaucoup d’options** avant de se fixer sur une direction.

## 4. Décider ce qui est « bon » ou pas

C’est là que la démarche devient plus « ingénierie » : ils ne se fient pas uniquement au goût personnel.

### Critères objectifs de bon design web

Un bon design de site est généralement jugé sur :

- **Clarté en 3 secondes** : comprend-on immédiatement l’activité et la valeur proposée ? 
- **Hiérarchie visuelle** : le regard est-il guidé vers les éléments importants (titres, CTA, infos clés) ?
- **Lisibilité** : taille de police, contraste, espacement, surtout sur mobile.
- **Cohérence** : mêmes styles, mêmes composants, mêmes règles sur toutes les pages. 
- **Performance** : temps de chargement, légèreté, optimisation mobile
- **Conversion / action** : l’utilisateur sait-il quoi faire et peut-il le faire facilement ? 

Ils se posent des questions très concrètes :  

- « Sur mobile, le texte se lit-il sans effort ? » 
- « Le moyen de contact est-il visible sans scroller ? »
- « La page se charge-t-elle vite sur une connexion mobile ordinaire ? » 

### Méthodes de décision

- **Design critiques en équipe** : revues collectives où chacun explique ce qui fonctionne / bloque, en se basant sur des principes (contraste, alignement, proximité, espace blanc, etc.). 
- **Checklists et heuristiques UX** : listes de critères (ex : 7 principes de design web : contraste, hiérarchie, alignement, proximité, répétition, équilibre, espace blanc). 
- **Tests utilisateurs** : montrer des prototypes à de vrais utilisateurs et observer où ils bloquent, ce qu’ils comprennent ou pas. 
- **A/B testing** : comparer deux versions (ex : deux titres, deux couleurs de CTA) et mesurer laquelle convertit mieux. 

Le « bon » design est donc celui qui **passe les tests** (compréhension, usage, conversion), pas seulement celui qui plaît au designer. 

## 5. Prototyper et itérer

Une fois une direction choisie :

- Ils créent des **maquettes UI** (couleurs, typographies, images, composants). 
- Puis des **prototypes interactifs** (clics, transitions, micro-interactions).
- Ils font des **boucles de feedback** : client, équipe, utilisateurs → ajustements → nouveau test. 

Le processus est itératif : on ne cherche pas la solution parfaite du premier coup, on **améliore progressivement** en fonction des retours et des données.

## 6. Cadre méthodologique courant : Double Diamond / Design Thinking

Beaucoup de designers-ingénieurs suivent un cadre comme le **Double Diamond** ou le **Design Thinking** :

- **Discover / Empathize** : comprendre utilisateurs et contexte. 
- **Define** : formuler clairement le problème à résoudre. 
- **Develop / Ideate** : générer plein d’idées, wireframes, concepts.
- **Deliver / Prototype & Test** : prototyper, tester, itérer, livrer.

Ce cadre garantit qu’on passe du temps sur la **bonne problématique** avant de se précipiter sur les solutions.
